* rationale
** functional with dynamic emphasis 
- no carry over of oops
- immutable data + first-class functions
- could always be done in lisp, by discipline/convention
  - but if a data strcuture can be muted, dangerous to presume it wont be
  - in traditional lisp, only the list data strcuture is structurally recursive 
- all data structures are immutable & persistent, supporting recursion
- dynamically typed (like erlang); pure functional languages (like ml, haskell) tend to strongly static types #
  - heterogenous collections, arguments and return types 
  - not everyone, or every task
  - expresssion problem: type related 
- expression problem: how to add both new types (easy in oops languages) and new functions (easy in functional languages) later, without breaking old code - protocols and multimethods 
- embraces run time polymorphism (interfaces of java, clos). no switch statements are required.
** lisp
*** why?
- often emulated / pillaged, still not duplicated 
- lambda calculus yields an extremely small core
- almost no syntax
- core advantage still code-as-data and syntactic abstraction (compiler or evaluator to create macros or syntactic extension > lanugae designers > we can build things)
*** what about standard lisps (cl / shceme)
- slow / no innnovation post standardization
- core data structures mutable, not extensible #
- no concurrency in specs
- good implementations already exist for jvm (abcl, kawa, sisc et al)
- standard lisp are their own platforms (island)
*** clojure is a lisp 
- not constrained by backwards compatiblity
- repl
- extends code-as-data paradigm to maps and vectors
- defaults to immutablity 
- core data structures are exdtensible abstractions #
- embraces a platform (jvm) - unification of types
** jvm hosted
- a new language should target a vm instead of rebuilding interpeter, runtime, gc, bytecode, type systems, libraries, et al
  - solved problems: talking to internet, talking to database 
- vms, not oses, are the target platforms of future languages, providing:
  - type system
    - dynamic enforcement and safety
  - libraries
    - huge set of facilities
  - memory and other resource management
    - gc is platform, not language, facility
    - hotspot optimization
  - byte code + jit compilation 
- language as platform vs language + platform
  - old way - each language defines its own run time 
  - new way - common runtime independent of language 
  - platforms are dictated by clients - huge investments in performance, scalablity and securty, et al
- object orientation is overrated
  - born of simulation, now used for everything, even when inappropriate
    - encouraged by java/c# in all situations, due to their lack of (idiomatic) suppprt for anything else
  - mutable stateful code is the new spaghetti code
    - hard to understand, test and reason about
    - concurrency disaster
- polymorphism is good
  - inheritance is not the only way to do polymorphism 
  - switch statements, structural matching, etc yield brittle systems
  - polymorphism yields extensible, flexible systems
  - clojure multimethods decouple polymorphism from oo and types
    - supports multiple taxonomies
    - dispatches via static, dynamic or external properties, metadata, etc
** thread-aware
- c++ has locks, semaphores, mutexes is really painful 
- concurrency and state in multi-core future
- immutabkity makes much of the problem go away
  - shares freely between threads 
- but changing state a reality for simulations and for in-program proxies to the outside world
- lockingn is too hard to get right over and over again
- software transactional memory does the hard part

** dynamic development

** lisp
- clojure is lisp 1 (common lisp is lisp 2)
  - functions and variables live in same list so cannot have same name
  - symbols are distinguished from places
  - risk: incidental aliasing (be careful) 
- reader
  - code-as-data - language itself is defined as list data structure (unlike other languages) 
  - extended for maps and vectors
- macros (defmacro) - common lisp and scheme have different approach to macros
  - supports overloading by arity
** functional programming
- first class citizens (understand make-adder function) - function is a value - you can save it, pass it, return it, and store it
  - give function a name
  - pass a function to another function
  - return a function from another function
  - put functions in collections
- variable arity - function overloading
  - use ([]) ([x]) for few fixed cases
  - use [& args] when you want any number
- immutable data structures
  - (lists), [vectors], {maps}, #{set}
  - value based equality semantics
    - henry baker - equals
  - exception: boxes (atom/def) and java interop are mutable 
  - reader (R -> e -> p -> l; repl) 
    - translator (text in -> clojure data out) 
    - reader error - your text is bad (syntactic, typos)
      - example: Unmatched delimiter, EOF while reading, Map literal must contain 
    - eval error - your code is bad (logic, types, names)
      - Unable to resolve, Wrong number of args, ClassCastException, ArityException
  - backquote support
    - ' = quote - reads + eval stops + keep as is
    - ` = backquote - reads + eval stops + keep as is + add namespaces + let you insert with ~ / ~@.
- fn is lambda
** persistant data structures 
- not db persistance
  - persistent = safe functions (no suprise bugs) + free undo + safe for threads + fast UI checks
  - you get safety without paying big copy cost
- old version of the collection is still available after the 'change'
- collection maintains its performance guarentees for most operations
  - therefore new versions are not full copies
- log base 32; billion things > 5 step process max
  - insertion speed may not match java
  - lookup speed may be better than java 
- hash map and vector both based upon array mapped hash tries (bagwell)
- sorted map is red-black tree 
- all core data is persistant
  - [] vector -> 32-way trie
  - {} map -> Hash Array Mapped Trie (HAMT)
  - #{} set -> same as map
  - () list -> linked list
** extensible abstractions
- clojure uses java interfaces to define its core data structures
- supports extensions to new concrete implementations
  - library functions will work with these extensions 
- big improvement vs hardwiring a language to the concrete implementations of its data types
*** example: the Seq abstraction
- highlights
  - write one function, works on all data
  - enables lazy seqs - values made only when needed
  - seq is not a list. it is a promise: "you can walk me with first/rest". all Clojure collections
 keep that promise
- works on [], {}, #{}, (), str ; everything is a list 
- collection is real data store; seq is view (abstraction) of it 
- first, rest, next, cons 
- two rules
  - (seq []) -> nil - empty seq is nil, not ()
  - next vs rest: rest never nil -> (), next gives nil when empty
- an abstraction of cons
  - first (car) and rest (cdr) are functions
  - immutable and persistent
  - can be implemented lazily
- many implementations
  - all collections provide seqs
  - can get seqs over java iterables and arrays
- library functions (map reduce filter etc) work with all seq
*** lazy seqs
- haskell is always lazy
- seqs can be used as interators or generators of other languages 
- seq, take, lazy-cons (macro), cycle
- lazy = recipe, not cake. Bake only when you eat
- good for infinite + save work. Bad for file handles. Use doall/vec when you need it now
